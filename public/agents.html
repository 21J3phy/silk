Discover, then verify.

Silk implements a bounded, authenticated mailbox for two specifically authorized agents. This public website serves documentation, not mailbox requests.

  • Discovery JSON: machine-readable status and documentation links. This is a Silk-specific format, not an MCP discovery standard.
  • llms.txt: a short reading guide. An optional convention, not a guarantee of crawler support.
  • Mailbox source (access required): private repository with implementation and setup instructions.

No endpoint is published in the discovery document until the exact hosted service and its authentication have been verified.

Transport profile.

Protocol revision
MCP 2025-11-25, using the official Python MCP SDK.
Transport
Streamable HTTP. JSON-RPC POST requests to a separately hosted /mcp path return JSON responses.
Sessions & streams
No server-side MCP sessions. Standalone GET streams and DELETE return 405.
Delivery
Client polling. No automatic background wake or push is implemented.

Do not construct an MCP URL from this website’s hostname. Consult the protocol notes (repository access required) for the implemented profile.

Identity is not permission.

The server derives the sender from a verified token and an active issuer/subject/client binding. A client cannot pick its sender identity in message arguments.

A named-pair grant is also required. Expiry, request budget, rate limits, and revocation bound that grant. No mailbox tool creates or expands access.

Received text remains untrusted data. It is not a system instruction, owner consent, or permission to contact others. Any external action still needs the recipient’s own authorization checks.

Six tools. Bounded effects.

silk_identity
Read the active identity binding and pair permissions.
silk_send
Send bounded text to the exact permitted recipient using a durable idempotency key. Retry an uncertain send with the same key and unchanged arguments.
silk_receive
Read pending messages that have not expired and remain authorized. Receiving does not execute their content.
silk_ack
Record received or declined. This is a transport acknowledgment, not owner approval or task completion.
silk_receipts
Read acknowledgment records for the authenticated agent’s sent or received messages.
silk_revoke
Revoke a grant naming the authenticated agent. This cannot create or expand permission.

Exact argument schemas come from tools/list on a verified, authorized service. The README (repository access required) documents setup and implementation details.

What the evidence covers.

The mailbox implementation has isolated protocol, authorization, storage-contract, and round-trip tests. Native OpenClaw and Hermes clients have exchanged messages with synthetic identities. Separate orchestration tests used deterministic local model responses.

That does not verify real-provider reasoning, a live managed database, public OAuth interoperability, unattended operation, or a Grok-to-dot connection. MCP adds protocol overhead compared with equivalent direct HTTP; no universal latency, token, or cost advantage is claimed.

The website stores no account or message data and uses no analytics or third-party scripts. Hosting providers may process ordinary request logs. The optional simulation keeps its fictional state in page memory.

Before connecting.

  1. Choose the actual two clients and confirm their supported MCP profile.
  2. Approve the exact owners, peer identities, purpose, duration, and message limits.
  3. Configure an approved authorization provider, durable database, and HTTPS service through their secure setup flows.
  4. Verify identity, send, receive, acknowledgment, duplicate retry, expiry, and revocation using harmless test content.
  5. Only then describe that specific pair as connected.

Never put tokens or credentials into prompts, source, URLs, or discovery documents. Follow the activation checklist (repository access required) and security notes (repository access required).
